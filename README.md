# СВОД — портал внутренней экспертизы рабочей документации

Инженер отдела внутренней экспертизы застройщика получает от проектного бюро
комплект рабочей документации: 4–6 томов PDF по разделам, каждый на 100–150
листов формата А1. Его работа — понять, что прислали, и найти несоответствия
до того, как по этим чертежам начнут строить. Сегодня это несколько часов
листания PDF на каждую подачу.

Портал забирает подготовительную часть: разбирает комплект, сверяет то, что
бюро объявило в общих данных, с тем, что реально лежит в файле, и предлагает
эксперту список позиций спецификации, которые стоит проверить на чертежах.

Разбор детерминирован: LLM не используется нигде. Машина сортирует и объясняет
причину, решения принимает человек.

## Что уже работает

| Этап | Что делает | Где |
|---|---|---|
| Приёмка | Состав комплекта, типы листов, номенклатура оборудования, флаги готовности к проверке | `agent/api.py: intake` |
| Этап 1 — паспорт тома | Ведомость чертежей, ссылочные и прилагаемые документы, комплекты раздела, нормативная база со статусами, условные обозначения картинками, регистрация изменений — и **расхождения** между объявленным и фактическим | `agent/general.py`, `symbols.py`, `norms.py`, `api.py: passport` |
| Этап 2 — план проверки | Ранжирование позиций спецификации по критичности с объяснением причины и колонкой «чем проверяется»; отбор эксперта галочками | `agent/criticality.py`, `api.py: checkplan` |
| Этап 3 — сверка с чертежами | Пересчёт марок спецификации на планах и схемах: штучные позиции с множителем типовых этажей, метраж по подписям и по измерению геометрии, кабели по кабельному журналу, светильники по ведомости освещения. Расхождения помечены классом позиции из плана проверки | `agent/match.py`, `measure.py`, `cable_journal.py`, `api.py: reconcile` |
| Замечания | Решение эксперта по каждому расхождению — из паспорта и из сверки: формулировку для бюро машина предлагает, эксперт правит и подписывает. Снятые расхождения не возвращаются после пересверки | `portal/remarks.py` |
| Лист чертежа | Просмотрщик с зумом кропом, метка замечания кликом по листу, подсветка мест, где машина нашла марку. Замечание из сверки или паспорта знает свои листы: из списка замечаний — ссылка «на листе», в полосе листов — счётчик и фильтр «с замечаниями», координаты подбираются автоматически при первом открытии | `agent/render.py`, `portal/sheets.py` |
| Письмо бюро | Замечания всей подачи одним документом .docx: шапка, объект, перечень по томам с листами, подпись эксперта | `portal/letter.py` |
| Выгрузка | Приёмка комплекта и паспорт тома вместе с планом проверки, сверкой и замечаниями — в xlsx, до десяти листов, с решениями эксперта и их авторами | `portal/exporting.py` |

Дальше по плану — диалог с бюро по замечаниям и PDF с аннотациями
(`ANNOTATIONS_PLAN.md`), затем проверка достаточности проектных решений (этап 4).
Планы: `ANNOTATIONS_PLAN.md`, `PASSPORT_PLAN.md`, `PORTAL_PLAN.md`, `AGENT_PLAN.md`.

## Устройство

```
agent/     пайплайн разбора PDF. Не знает про портал и про БД.
           api.py — единственная точка входа: intake / passport / checkplan
portal/    веб-портал: модель данных, воркер, шаблоны.
           Не знает про pymupdf: любая работа с файлом — задача в очереди
```

Правило одно: портал не открывает PDF, `agent/` не знает про портал. Обе
стороны общаются через `agent/api.py`, и CLI `python -m agent.run` продолжает
работать как раньше.

Функция `checkplan()` PDF не открывает вообще: пересчёт плана после правки
порогов стоит доли секунды, а не двадцать минут повторного разбора тома.

Сверка (`reconcile`) считается один раз и в одном месте: CLI `python -m
agent.run` и портал вызывают один фасад, второй копии счёта нет. Запускается
она руками с вкладки — читает все планы и схемы тома, и это минуты, а не
секунды.

## Стек

FastAPI + Jinja2 + HTMX, PostgreSQL 16 + SQLAlchemy 2 + Alembic, RQ поверх
Redis, pymupdf для разбора, S3-совместимое хранилище (Cloudflare R2) для томов
и картинок условных обозначений, openpyxl для выгрузок и python-docx для
письма бюро. Python 3.12.

Сборки фронтенда нет и не планируется: чекбокс шлёт `hx-post`, сервер
возвращает перерисованную строку и счётчик.

## Запуск на ноутбуке

Без Postgres, Redis и облачного хранилища — на SQLite, с файлами на диске
и разбором в потоке веб-процесса:

```bash
pip install -r requirements.txt
python run_local.py          # http://127.0.0.1:8099
```

Дальше — «Новый объект», перетащить PDF, дождаться разбора.

## Проверки

```bash
python -m agent.tests_general       # разбор общих данных и картинки УГО
python -m agent.tests_norms         # нормативная база
python -m agent.tests_criticality   # модель критичности
python -m agent.tests_passport      # расхождения и фасад
python -m agent.tests_match         # сверка с чертежами (на реальном томе ~1 мин)
python -m agent.tests_render        # картинка листа, координаты меток, поиск марок
python -m agent.tests_quantities    # количества и марки
```

Часть проверок работает на реальных томах из `Example/` (в репозиторий не
входят). Если файлов нет, проверка честно пишет «пропущен» и идёт дальше.

## Продакшен

`render.yaml` — блюпринт Render: веб, воркер, Postgres, Key Value. Ограничения
площадки, под которые согнута архитектура, описаны в комментариях к файлу;
главное — постоянный диск монтируется только к одному сервису, поэтому файлы
всегда во внешнем объектном хранилище, а воркеру нужно 2 ГБ памяти.

Переменные окружения — в `.env.example`. Для загрузки из браузера в бакет
нужен CORS, JSON лежит в `README_PORTAL.md`.

## Что важно знать, прежде чем править

- **Реестр нормативов** `agent/norms_registry.yaml` ведёт эксперт руками.
  Машина не выдумывает статусов: чего нет в реестре, то показывается как
  «нет в реестре». Первичное наполнение собрано по пяти реальным томам
  и должно быть выверено перед первой настоящей подачей.
- **Класс позиции пишет машина, решение — эксперт.** Это два независимых
  поля (`check_item.cls` и `check_item.decision`), и путать их нельзя:
  булев флаг «включено» либо затирался бы повторным разбором, либо не давал
  бы машине ничего предлагать.
- **Решения хранятся по ключу позиции**, а не по id строки спецификации:
  при повторном разборе id меняются, позиция остаётся той же.
- **Массовые действия не трогают строки с решением эксперта**, пока он явно
  не попросит перезаписать.
- **У замечания два разных понятия «лист».** `sheets` — листы, к которым оно
  относится (их знает машина: там встречена марка); `page` и `anchor` — где
  стоит метка. Первое есть всегда, второе появляется, когда эксперт открыл
  лист или поставил метку руками.
- **Якорь метки не переносится между подачами.** Само замечание переносится
  по ключу, а координаты принадлежат конкретному файлу: в новом файле бюро
  тот же узел лежит на другой странице. Рядом с якорем хранится
  `anchor_document_id` — из какого тома он взят.
- **Координаты меток живут в долях отрисованной картинки.** Текстовый слой
  PDF — в неповёрнутой системе, `page.rect` — в повёрнутой; перевод сделан
  один раз в `agent/render.py` и проверяется тестом `tests_render`.
- **Замечание живёт отдельно от строки сверки.** Пересверка переписывает
  `match_item` целиком, поэтому решение эксперта хранится в `remark` и
  связывается ключом «вид + каноническая марка». Снятое расхождение после
  пересверки не возвращается как непросмотренное, а замечание, чья строка
  исчезла, помечается в списке: возможно, бюро исправило чертёж.
