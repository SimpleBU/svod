# План: портал приёмки проектной документации

Комплект от бюро загружается → портал показывает состав, номенклатуру и расхождения.
Поверх существующего пайплайна `agent/`, без его переписывания.

Спутник к `AGENT_PLAN.md`: там — как агент разбирает расхождения, здесь — как всё это
становится продуктом. Агентская часть встраивается в воркер на неделях 4–6.

---

## 1. Кто платит и что это меняет

Покупатель — **внутренняя экспертиза застройщика**: люди, принимающие чужую
документацию и обязанные найти проблемы до стройки.

Формулировка ценности не «сервис проверяет проект» (накажут на первой пропущенной
ошибке), а «портал показывает, что именно прислали, и сокращает объём ручной сверки,
честно помечая, что осталось на человека».

Три следствия для архитектуры — заложить сразу:

- **Единица работы — комплект, а не файл.** Бюро присылает 5–8 томов (ЭОМ, ОВ, ВК,
  АСУД, ПРК). Эксперт мыслит объектом и подачей.
- **Ревизии не «потом».** В `Example/` уже «Изм. 1-4», «изм.1,2». Главный вопрос
  эксперта на второй подаче: что изменилось и какие замечания закрыты. Схема данных
  обязана это выдерживать с первого дня, даже если UI появится на третьей неделе.
- **Выходной артефакт — лист замечаний, а не xlsx-сверка.** Xlsx вы уже умеете.
  Продаётся то, что эксперт отправляет обратно в бюро за своей подписью.

**Главное решение:** первая задача портала — не сверка, а **приёмка**: состав
комплекта, номенклатура, готовность к сверке. Дешевле в разработке (нужен только
`extract.py`), даёт пользу за пять минут работы эксперта, служит входом для остального
и не содержит ни одного вызова LLM.

## 2. Контур

```
браузер ──presigned PUT──> R2 (файлы)
   │
   └── web (FastAPI+HTMX) ──> Redis/RQ ──> worker ──> agent/api.py ──> Postgres
```

- Веб никогда не открывает PDF сам. Любая работа с документом — задача в очереди
  с прогрессом, иначе первый же том на 50 МБ повесит запрос.
- Браузер льёт файл прямо в хранилище по подписанной ссылке: снимает таймаут,
  расход трафика Render и пиковую память веба.
- Прогресс пишется в поле прогона в Postgres, не в Redis: перезапуск воркера
  не теряет историю.

---

## 3. Стек (площадка — Render)

| Слой | Выбор | Почему |
|---|---|---|
| Веб | FastAPI + Jinja2 + HTMX | Один Python-репозиторий, ноль сборки JS |
| Очередь | Render Key Value (Redis) + RQ | Free 25 МБ хватает: в Redis только id задач |
| БД | Render Postgres + SQLAlchemy 2 + Alembic | Веб и воркер — разные машины, SQLite невозможен |
| Файлы | S3-совместимое (Cloudflare R2 / B2) | **Не диск Render** — см. ниже |
| Загрузка | presigned PUT из браузера | Том 50 МБ не идёт через веб-сервис |
| Деплой | `render.yaml` (Blueprint) | Все сервисы одним файлом, push → деплой |
| Авторизация | сессии + пароль | `org_id` во всех таблицах с первого дня |

### Три ограничения Render, под которые гнём архитектуру

1. **Persistent disk монтируется только к одному сервису** и недоступен второму.
   Веб и воркер общий диск иметь не могут → внешнее объектное хранилище обязательно
   с первого дня. Всё вне диска стирается при каждом деплое.
2. **Free-инстанс — 512 МБ.** `pymupdf` на томе 40–50 МБ с рендерами и измерением
   геометрии в них не влезет: воркер будет молча убиваться по OOM. Воркеру нужен
   `1c-2g` (~$25/мес), веб живёт на $7.
3. **Free web service засыпает** без запросов — на демо заказчику это выглядит
   как поломка.

Ориентир по стоимости контура на пилот: web $7 + worker $25 + Postgres ~$6 +
Key Value $0 + R2 ~$1 ≈ **$40/мес**. Цены проверять по актуальному прайсу.

Не берём: Streamlit (роли/очередь/комментарии делаются криво), Celery (избыточен),
диск Render под файлы, хранение результата только в xlsx (портал превратится
в файлопомойку — ни фильтров, ни замечаний, ни диффа ревизий).

Приложение от площадки не зависит: тот же код ставится в закрытый контур
застройщика как `docker compose`, отличаются реализация `Storage` и env.

## 4. Фасад пайплайна

Правило: портал не знает про pymupdf, `agent/` не знает про портал. Между ними —
один модуль. CLI обязан продолжать работать: это режим отладки и запасной вариант.

```python
# agent/api.py — единственная точка входа для портала

@dataclass
class Sheet:   page:int; kind:str; code:str|None; title:str|None; mult:int
@dataclass
class SpecRow: pos; name; mark; unit; qty; section; note; excluded; parent_pos

@dataclass
class Capabilities:
    has_spec: bool                  # без неё сверка невозможна — сказать сразу
    has_cable_journal: bool         # .КЖ -> точный метраж кабеля
    has_lighting_list: bool         # ведомость освещения -> точный счёт светильников
    has_vector_geometry: bool       # Revit 1:1 -> измерение труб возможно
    rotated_spec: bool
    unreadable_font_pages: list[int]  # «unknown cid font», как в АСУД

def intake(pdf, progress=None) -> IntakeResult:
    """classify_pages + parse_spec. Без сверки — быстро."""

def reconcile(pdf, progress=None) -> ReconcileResult:
    """Существующий process(), но возвращает rows/unrows/sheets/notes."""

def export_xlsx(result, path):
    """report.write_report как есть — теперь кормится из БД."""
```

`Capabilities` — самая недооценённая часть. Это ответ на вопрос эксперта
«насколько машине можно верить по этому тому». Спецификации нет — сверка не
запускается. Кабельного журнала нет — метраж пойдёт с допуском. Половина листов
АСУД с нечитаемыми шрифтами — так и пишем на экране, а не молча выдаём
«нет на чертежах».

Прогресс: `progress(stage, done, total)`, воркер пишет в `run.progress` раз в секунду
с троттлингом. Стадии естественные: классификация листов, разбор спецификации, счёт
по планам, счёт по схемам, измерение геометрии, сверка. Эксперт видит не крутилку,
а «идёт счёт по схемам, лист 84 из 213».

## 5. Модель данных

Всё с `org_id` и `created_at`.

| Таблица | Ключевые поля | Смысл |
|---|---|---|
| `org` | name, plan, limits | Тенант = застройщик |
| `user` | email, role, org_id | админ / эксперт / наблюдатель |
| `project` | name, code, bureau | Объект строительства |
| `submission` | project_id, label, received_at | **Подача комплекта**: «Изм. 1», «Изм. 2» |
| `document` | submission_id, section, cipher, file_key, pages | Том PDF; section по шифру |
| `sheet` | document_id, page, kind, code, title, mult, kind_override | Лист; override — ручная правка эксперта |
| `spec_item` | document_id, pos, name, mark, unit, qty, excluded, parent_pos | Строка спецификации |
| `nomenclature` | project_id, canon_mark, name, unit, qty_total, sources jsonb | **Сводная по объекту** |
| `run` | kind, status, progress, stats jsonb, error, cost | intake / reconcile / agent |
| `finding` | document_id, mark, qty_spec, qty_plan, qty_schema, status, pages[], source | Строка сверки; source = откуда цифра |
| `remark` | finding_id, author_id, text, state, carried_from | **Замечание эксперта** |

`run.stats` и сырой результат пайплайна — в jsonb рядом с нормализованными таблицами:
пока схема ходит ходуном, спасает от миграций на каждый чих.

## 6. Экран приёмки

**Вкладка «Состав комплекта».** По каждому тому: шифр, раздел, число листов,
разбивка по типам (планы / схемы / спецификация / КЖ / ведомости / приложения).
Рядом — флаги готовности из `Capabilities` по светофору: спец. найдена, .КЖ есть,
ведомости освещения нет, 17 листов нечитаемы.

**Вкладка «Номенклатура объекта».** Сводная по всем томам: канонизированная марка,
наименование, единица, количество, где встречается. Сразу видны три вещи, которые
эксперт ищет руками: дубли между разделами, позиции без марки (машинной сверке
не поддаются), исключённые изменением строки.

Обе — с поиском, фильтром и выгрузкой xlsx. Это весь объём первого дня.

Почему продаётся само: приёмка комплекта сегодня — несколько часов ручного листания
на каждую подачу, и делается она до всякого анализа. Портал закрывает её целиком,
детерминированно и воспроизводимо, без единого вызова модели.

## 7. День первый

Цель — приёмка, **работающая на Render** на пяти томах из `Example/`.

| Время | Что |
|---|---|
| 0:00–0:45 | Скелет + `render.yaml` + деплой пустышки. Деплой **первым**, не последним: сюрпризы Render стоят 20 минут здесь и вечер — потом |
| 0:45–1:45 | Модели, Alembic, S3-адаптер к R2, presigned-загрузка, раздел по шифру имени |
| 1:45–3:15 | `agent/api.py: intake()` — обёртка, дата-классы, прогресс, `Capabilities`. Проверить, что `python -m agent.run` жив |
| 3:15–4:45 | Воркер и очередь: скачать → разобрать → записать → прогресс. Страница проекта с HTMX-polling |
| 4:45–6:45 | Экран «Состав комплекта» с флагами готовности |
| 6:45–8:15 | Экран «Номенклатура»: канонизация из `match.py`, дубли, без марки, исключённые |
| 8:15–9:00 | Экспорт xlsx в стилях `report.py` |
| 9:00–10:00 | Прогон на Render (не локально): 5 томов, замер памяти и времени на 51-мегабайтном ОВ1 |

**Режем:** сверка в вебе, аутентификация (одна захардкоженная организация, но
`org_id` в схеме есть), роли, замечания, PDF-вьюер, ревизии, отмена задач, письма,
биллинг, любой LLM.

**Три вещи, которые сорвут день:**

- Рефакторинг `agent/` «заодно». Обёртка — да, переписывание `match.py` — нет:
  там 34 КБ выстраданной логики.
- Красивый UI. Таблицы, ссылки, светофор из готовых цветов отчёта.
- Разработка только локально. На ноутбуке всё влезет в память и таймауты;
  первый прогон тяжёлого тома — на реальном инстансе, в первой половине дня.

## 8. Роадмап

| Когда | Что | Зачем сейчас |
|---|---|---|
| День 1 | Приёмка: загрузка, состав, номенклатура, xlsx — на Render | Ядро есть, LLM не нужен, ошибиться негде |
| Дни 2–3 | Сверка в портале: обёртка над `process()`, таблица находок, ссылки на листы | Отложено осознанно: требует настройки памяти и таймаутов под тяжёлый том |
| Неделя 1 | Рабочее место эксперта: аккаунты и роли, PDF-вьюер (pdf.js) с переходом на лист-доказательство, замечания со статусами, экспорт **листа замечаний** в docx | Портал становится местом, где делается работа. Лист замечаний — то, за что платят |
| Недели 2–3 | Ревизии: подача «Изм. 2», дифф номенклатуры и находок, автоперенос открытых замечаний, ручная правка классификации листов | Второй заход бюро — где ручная работа больнее, а машина сильнее. Правка классификации даёт данные, чем ошибаются правила |
| Недели 4–6 | Агент: этапы 1–3 `AGENT_PLAN.md` в воркере — провайдер, триаж, класс B, вердикты с обязательным evidence, учёт стоимости по тенанту | К этому моменту в БД накоплены реальные проблемные строки: есть на чём собрать золотой набор и мерить, а не верить |
| Далее | Агентский цикл с кропами (классы A и C), on-prem-образ, SSO, биллинг, второй профиль оформления | Развилка по цифрам пилота, а не по плану, написанному сегодня |

**Развилка недели 3.** Третий путь из `AGENT_PLAN.md` — «в точность правил»:
ведомость осветительного оборудования как второй точный источник, разбор марки ЭОМ
на серию и номинал. Часть того, что хочется отдать модели, правила закрывают
надёжнее и бесплатно. Решать после первых цифр пилота.

## 9. Тариф

Застройщик покупает снятые человеко-часы экспертизы и уменьшенный риск переделок.

- **Пилот — фикс за один объект.** Одна подача, одна команда, две недели. Задача
  пилота не заработать, а получить цифру: сколько часов проверки сняли.
- **Дальше — подписка на команду экспертизы** с лимитом объёма (листов или подач
  в месяц). Не за найденные ошибки: платить за их количество никто не станет,
  а вас это подтолкнёт их выдумывать.
- **On-prem — отдельная лицензия.** Тот же compose в их контуре. Просить будут
  раньше, чем вы будете готовы.

Метрика в каждое коммерческое предложение: **доля позиций, закрытых машиной без
участия человека.**

## 10. Риски

| Риск | Вес | Что делать |
|---|---|---|
| **Ложное «ок»** — портал сказал «сходится», позиции на чертежах нет | убивает | Никогда не показывать «проверено» без источника вывода. Колонка происхождения цифры в каждой строке, отдельные статусы для машинных и модельных выводов, дисклеймер «не является заключением экспертизы» |
| **Конфиденциальность** — проекты застройщика на Render и в R2 | блокер сделки | СБ спросит про площадку раньше, чем про функции. Ответ готовить заранее: тот же compose в их контуре, `LocalStorage` вместо R2, срок хранения и удаление по кнопке |
| **Память воркера** — OOM на тяжёлом томе | высокий | Инстанс не ниже 2 ГБ, закрывать документ сразу после разбора, не держать рендеры в памяти, тома по одному. Замерить на ОВ1 в первый день |
| **Эфемерная ФС Render** | ловушка | Всё мимо хранилища исчезает при деплое. Временные файлы — только в tmp внутри задачи, результат — в БД или R2 немедленно |
| **Второе бюро — другое оформление** | высокий | Экран классификации листов с ручной правкой: деградация видима и исправима пользователем. Профиль оформления как сущность, а не ветвления в коде |
| **Тяжёлые тома** — 50 МБ, 200+ листов, геометрия | высокий | Постадийный прогресс, таймаут и отмена, воркер в один поток, кэш по хешу файла: переподача часто отличается двумя листами из двухсот |
| **Отчёт как юридический документ** | средний | Формулировки «требует проверки», «не найдено автоматически». Подпись ставит эксперт, а не портал |
| **Расползание в дне-1** | управляемо | Список «режем» — контракт с самим собой |
