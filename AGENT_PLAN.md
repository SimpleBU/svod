# План: гибридная агентная система сверки

Пайплайн считает → агент разбирает расхождения → отчёт с вердиктами.

Документ объясняет **как** это устроено и **в каком порядке** строить. Код здесь — эскизы для понимания контрактов, не готовые модули.

---

## 1. Где кончается пайплайн и начинается агент

Сейчас `agent/run.py` — прямая линия без ветвлений:

```
PDF → classify_pages → parse_spec → build_vocab/build_m_vocab
    → count_on_pages (Планы, Схемы)
    → count_lengths_on_pages / measure_plan_pages / parse_journal
    → reconcile → write_report → xlsx
```

`reconcile()` возвращает `rows` — список словарей, каждый со `status` из пяти значений:

| статус | что значит | кто разбирается |
|---|---|---|
| `ок` | сошлось по обоим источникам | никто |
| `ок (частично)` | сошлось по одному | никто (или дешёвая проверка) |
| `расхождение` | цифры не бьются | **агент** |
| `нет на чертежах` | марка не найдена | **агент** |
| `есть на чертежах, метраж не подписан` | нашли, посчитать нельзя | **агент** |

Ключевая мысль: **пайплайн не переписывается**. Агент — это фильтр между `reconcile()` и `write_report()`, который берёт проблемные строки, смотрит на страницы PDF глазами и меняет `status` + добавляет объяснение. Правила считают точнее любой модели; LLM нужен там, где счёт вообще невозможен формально.

```
reconcile → rows ──┬── ок / ок (частично) ─────────────────┐
                   │                                        ├→ write_report
                   └── проблемные → ТРИАЖ → АГЕНТ → вердикты┘
```

## 2. Триаж: что вообще отдавать модели

Отдавать всё подряд дорого и вредно — модель начнёт «подтверждать» то, что правила посчитали верно. Правило отбора: **агент вызывается только там, где у правил не хватило информации, а не там, где они дали ответ.**

Четыре класса задач, каждый со своим промтом (и, возможно, своей моделью):

**A. Позиция без марки** («шкаф металлический наружный», ВК/АСУД).
Правила ищут по строке — искать нечего. Агент смотрит рендеры планов раздела и считает объекты визуально/по подписям систем.
*Ожидание: понижает «нет на чертежах» до «найдено визуально, требует подтверждения».*

**B. Разный формат записи** — самое ценное. В ЭОМ на схеме `ДИФ-101 4Р` + `25A/100mA` двумя строками, в спецификации `16063DEK`. Строковый матч невозможен, семантический — тривиален.
*Ожидание: закрывает большую часть ложных «нет на чертежах» в ЭОМ.*

**C. Числовое расхождение** — спец. 12, план 9. Агент смотрит страницы и объясняет: три штуки на листе, который классифицирован как «приложение»; или множитель типовых этажей взят неверно; или позиция вычеркнута изменением.
*Ожидание: не исправляет цифру, а называет причину — это и есть работа, которую иначе делает человек.*

**D. Примечания и изменения** — текст «изм. 2: заменить на …», сноски, ведомости. Читается как текст, без картинок, дёшево.

Порядок внедрения: **B → C → A → D**. B даёт максимум пользы на наименьшей сложности.

## 3. Инструменты агента

Агент — это цикл «модель просит инструмент → мы выполняем → отдаём результат → модель решает». Без инструментов это не агент, а один вызов с картинкой. Минимальный набор, всё поверх уже написанного кода:

| Инструмент | Реализация | Зачем |
|---|---|---|
| `render_page(page, dpi, bbox=None)` | `pymupdf` `page.get_pixmap` + crop | Посмотреть лист или его фрагмент |
| `search_text(query, pages=None)` | `page.search_for` (нормализация марок — из `match.py`) | «А где вообще встречается 16063?» |
| `get_spec_row(mark)` | срез из `parse_spec` | Полная строка спецификации с примечаниями |
| `list_pages(kind)` | `classify_pages` | Какие листы Планы/Схемы/КЖ |
| `get_page_text(page)` | `page.get_text` | Дешевле картинки, когда хватает текста |

Правила по инструментам:

- **Никаких инструментов записи.** Агент не меняет xlsx и не трогает данные — он возвращает структуру, мы её применяем. Это делает систему предсказуемой и отчёт воспроизводимым.
- **Бюджет шагов** — жёсткий лимит (напр. 8 итераций и 6 рендеров на строку). Дальше цикл прерывается со статусом `не определено (лимит)`. Без лимита агент способен листать документ бесконечно.
- **Кроп важнее полного листа.** Лист А1 в 150 dpi — нечитаемая каша и ~1600 токенов. Правильно: `search_text` находит координаты → рендерим окрестность 2000×1500 px в высоком dpi. И дешевле, и точнее.

## 4. Контракт вердикта

Самое важное решение во всей системе. Модель возвращает **строго структурированный JSON**, и никакого свободного текста в отчёт не попадает:

```json
{
  "mark": "16063DEK",
  "verdict": "found | not_found | mismatch_explained | inconclusive",
  "confidence": 0.0,
  "found_qty": 12,
  "evidence": [
    {"page": 34, "bbox": [120, 800, 900, 1100], "quote": "ДИФ-101 4Р 25A/100mA"}
  ],
  "reasoning": "На схеме подписан серией и параметрами, артикул не указан.",
  "suggested_status": "ок (по описанию, требует подтверждения)"
}
```

Что здесь принципиально:

- **`evidence` обязателен и не пустой** для любого вердикта кроме `inconclusive`. Вердикт без ссылки на страницу и цитаты автоматически понижается до `inconclusive`. Это единственная реальная защита от выдумывания.
- **Валидация постфактум**: `quote` действительно ищется на странице `page` через `page.search_for`. Не нашли — вердикт отбрасывается. Дёшево и ловит почти все галлюцинации.
- **Отдельные статусы для агентских выводов.** Не переписывайте `расхождение` в `ок` — вводите `ок (по описанию)`, `найдено визуально`, `не определено`. Эксперт должен видеть, где считала машина, а где рассуждала модель. Иначе доверие к отчёту рушится на первой ошибке.
- **`confidence` — от модели, не метрика.** Использовать только для сортировки в отчёте, не для автоматических решений.

В отчёт добавляются колонки: `Вердикт агента`, `Обоснование`, `Страницы-доказательства`, `Модель`, `Стоимость`. Исходные `Кол-во Спец./План/Схема` и `Статус` остаются нетронутыми — рядом, для сравнения.

## 5. Мульти-LLM: абстракция провайдера

Вы планируете разные модели под разные задачи — значит абстракцию нужно закладывать сразу, а не рефакторить потом.

Тонкий слой: один интерфейс, реализации под провайдеров, роутинг по типу задачи.

```python
# agent/llm/base.py
class LLMProvider(Protocol):
    name: str
    supports_vision: bool
    supports_tools: bool

    def complete(self, *, system: str, messages: list, tools: list | None,
                 max_tokens: int) -> LLMResponse: ...

@dataclass
class LLMResponse:
    text: str
    tool_calls: list[ToolCall]
    usage: Usage          # in/out токены → стоимость
    stop_reason: str
    raw: dict             # для отладки
```

Реализации: `anthropic.py`, `openai_compatible.py` (закрывает Ollama, vLLM, GigaChat-совместимые шлюзы, локальные модели), `mock.py` (детерминированные ответы для тестов — без него не будет CI).

Роутинг конфигом, не кодом:

```yaml
# agent/llm/routing.yaml
tasks:
  format_mismatch:      # класс B — семантика, текст, вижн изредка
    provider: anthropic
    model: claude-haiku-4-5-20251001
    max_tokens: 1500
  visual_count:         # класс A — считать объекты на чертеже
    provider: anthropic
    model: claude-sonnet-5
    max_tokens: 4000
  notes_parsing:        # класс D — чистый текст
    provider: local
    model: qwen2.5:14b
  fallback:
    provider: anthropic
    model: claude-haiku-4-5-20251001
```

Три вещи, которые сэкономят вам недели:

1. **Не пишите свой универсальный tool-calling.** Форматы вызова инструментов у провайдеров расходятся. Приведите к своей внутренней структуре `ToolCall(name, args, id)` в адаптере — вся остальная система знает только её.
2. **Локальные модели почти наверняка не потянут чертежи.** Открытые vision-модели на плотной инженерной графике А1 сейчас слабы. Реалистичное разделение: облако — картинки, локально — текст (класс D, парсинг примечаний). Если данные проектов нельзя отдавать наружу — это блокер архитектуры, решать надо до написания кода, а не после.
3. **Учёт стоимости на уровне провайдера.** `Usage` в каждом ответе, сумма пишется в отчёт. Без этого через месяц будет непонятный счёт.

## 6. Структура модулей

```
agent/
  extract.py  match.py  measure.py  report.py  run.py   # как есть, не трогаем
  llm/
    base.py            # Protocol, LLMResponse, Usage, ToolCall
    anthropic.py       # адаптер
    openai_compat.py   # адаптер (Ollama/vLLM/шлюзы)
    mock.py            # для тестов
    router.py          # routing.yaml → провайдер по имени задачи
  agentic/
    triage.py          # rows → список DisputedCase с классом A/B/C/D
    tools.py           # render_page, search_text, get_spec_row, ...
    loop.py            # цикл вызова инструментов + бюджет шагов
    prompts/           # по промту на класс задач, в отдельных файлах
    verdict.py         # схема, валидация evidence, слияние в rows
    cache.py           # кэш по хешу (pdf + mark + класс + модель)
  config.py            # ключи из env, routing.yaml, лимиты
```

Встраивание в `run.py` — одна вставка перед отчётом:

```python
rows, unrows = reconcile(...)

if cfg.agent_enabled:
    cases = triage(rows, unrows, pages)              # только проблемные
    verdicts = run_agent(doc, cases, router, cfg)    # параллельно, с кэшем
    rows = apply_verdicts(rows, verdicts)            # новые колонки, старые целы

write_report(out, pdf_path.stem, rows, unrows, pages, notes)
```

Флаг `--agent` в CLI, по умолчанию **выключен**. Пайплайн обязан оставаться работоспособным без ключей и сети — это и режим отладки, и запасной вариант, и то, что вы показываете, когда API лежит.

## 7. Кэш, параллелизм, стоимость

**Кэш обязателен, а не «потом».** Ключ — `sha256(pdf_bytes) + mark + task_class + model`. Вы будете гонять один и тот же PDF десятки раз, подкручивая промты; без кэша каждый прогон платный и медленный. Хранить в `.cache/verdicts/*.json`.

**Параллелизм** — 4–8 строк одновременно (`ThreadPoolExecutor`), с ретраями на 429/529. Строки независимы, ускорение линейное.

**Порядок цифр** (текущие цены: Haiku 4.5 — $1/$5 за млн токенов, Sonnet 5 — $2/$10 до 31.08.2026, далее $3/$15):

| | на строку | 60 проблемных строк |
|---|---|---|
| Класс B/D (текст, Haiku) | ~$0.003 | ~$0.20 |
| Класс A/C (2 кропа, Sonnet) | ~$0.02 | ~$1.20 |

То есть полная обработка документа — **порядка доллара**. Проверять реальные цифры по счётчику `Usage`, а не по этой таблице; вижн-токены зависят от разрешения кропов, и именно они определят итог.

## 8. Как понять, что агент работает

Без этого пункта всё остальное — вера. Метрика должна существовать до первого промта.

1. **Золотой набор.** Возьмите 5 PDF из `Example/`, выгрузите ~50 проблемных строк, разметьте вручную (эксперт-проектировщик, полдня работы): что реально есть на чертежах, что нет, где ошибся пайплайн. Это единственная инвестиция, без которой не обойтись.
2. **Метрики на каждый прогон:**
   - *точность вердиктов* — совпало с разметкой / всего;
   - **ложноположительные — главная метрика.** Агент сказал «ок», а позиции на чертежах нет. Пропущенная ошибка в проекте стоит дороже лишней проверки. Целевое: <2%, при промахах загрубляйте промт в сторону `inconclusive`;
   - *доля закрытых строк* — сколько ручной работы снято;
   - *стоимость и время* на документ.
3. **Регресс на каждое изменение промта.** Один скрипт `eval.py`, кэш выключен, метрики в консоль. Промты меняются часто, и без регресса вы будете улучшать один класс, ломая другой, и не узнаете об этом.
4. **Мок-провайдер в CI** — тесты структуры и валидации без сети и без денег.

## 9. Порядок работ

| Этап | Что делаем | Результат | Срок* |
|---|---|---|---|
| 0 | Золотой набор: 50 размеченных строк | Есть на чём мерить | 1 д (нужен эксперт) |
| 1 | `llm/` — base, anthropic, mock, router + `config.py` | Вызов модели с учётом токенов | 1 д |
| 2 | `triage.py` + `verdict.py` + колонки в отчёте | Проблемные строки классифицированы, отчёт готов принять вердикты | 1 д |
| 3 | **Класс B без картинок** — только текст спецификации и страниц | Первая реальная польза: ЭОМ-аппараты перестают быть «нет на чертежах». Измерить по золотому набору | 2 д |
| 4 | `tools.py` + `loop.py` — рендеры, кропы, бюджет шагов | Настоящий агентный цикл. Классы A и C | 3 д |
| 5 | Кэш, параллелизм, ретраи, `eval.py` | Прогон папки за минуты, воспроизводимо | 1 д |
| 6 | `openai_compat.py` + локальная модель на класс D | Мульти-LLM работает, чувствительный текст не уходит наружу | 2 д |
| 7 | Обёртка в сервис (FastAPI + очередь) или Streamlit-MVP | Портал с ролями проектировщик/эксперт | отдельный трек |

\* Сроки — для одного разработчика, знающего этот код. Этапы 0–3 самодостаточны: если остановиться после третьего, у вас уже рабочий гибрид, покрывающий самый частый класс ложных расхождений.

## 10. Грабли

- **Не давайте агенту переписывать цифры.** Правила считают точнее. Задача агента — объяснить расхождение и найти то, что правила искать не умеют. Как только модель начинает «уточнять» количества, отчёт теряет воспроизводимость: два прогона дают разные числа, и эксперт перестаёт ему верить.
- **Полный лист А1 в 150 dpi модель не читает.** Только кропы вокруг найденного текста. Это одновременно и точность, и деньги.
- **Вердикт без `evidence` — мусор.** Валидируйте цитату поиском по странице, автоматически, всегда.
- **Не сливайте агентские статусы с машинными.** Отдельные значения, отдельная колонка «Модель». Эксперт должен видеть источник вывода.
- **Промты — файлы, а не строки в коде.** Они меняются каждый день, их нужно диффать в git и прогонять регрессом.
- **Решите вопрос конфиденциальности до этапа 1.** Если проектные PDF нельзя отправлять в облако, вся вижн-часть (классы A и C) отпадает, и остаётся только текстовая на локальной модели. Это другая система — лучше знать заранее.

## 11. Что дальше

Три развилки после этапа 3:

- **Вглубь** — этапы 4–6, полноценный агент с инструментами и мульти-LLM.
- **Вширь** — портал с ролями (промт под прототип уже готов): проектировщик загружает, воркер гоняет пайплайн + агент, эксперт комментирует, комментарии возвращаются в работу.
- **В точность правил** — известные пробелы из `agent/README.md`: «Ведомость осветительного оборудования» как второй точный источник по аналогии с кабельным журналом, разбор марки ЭОМ на серию/полюсность/номинал. Часть того, что вы хотите отдать модели, дешевле и надёжнее закрывается правилами. Класс B, например, наполовину решается разбором артикула — и стоит ноль.

Разумный порядок: этапы 0–3, замер на золотом наборе, и только после этого выбор развилки по фактическим цифрам.
